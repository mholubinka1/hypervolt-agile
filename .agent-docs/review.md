# Review Criteria (repo-specific)

Review criteria this repository has accumulated from its own Copilot review rounds.

- The `address-copilot-comments` skill appends a generalised, one-line criterion here for
  every Copilot finding on a PR that resulted in a code change. Findings that were pushed
  back on ("Ignored.") are never recorded — this file only holds criteria the team accepted
  by changing code.
- The `code-review` skill feeds this file to its Standards sub-agent alongside the skill's
  own `REVIEW-CRITERIA.md`, and treats the entries here as documented repo standards (a
  breach may be blocking).
- Prune stale entries, and promote durable ones into a shared criteria file, by hand.

Each entry is a bold label plus a one-line imperative rule, tagged with the PR it came
from — for example:
`- **Partial checks for compound state**: flag a readiness check that inspects one artefact when the state it gates has several parts. (PR #58)`

## Criteria

- **Unguarded cleanup sequences**: flag a teardown or failure-path cleanup that calls multiple release steps back-to-back with no individual guard — one step raising skips the rest and leaks whatever it would have released. (PR #100)
- **Non-native interactive elements without keyboard support**: flag a click handler attached to an element that isn't natively focusable (e.g. an SVG shape) with no `tabindex`, role, and keydown handling for Enter/Space alongside it. (PR #100)
- **Inputs without a real accessible name**: flag a text input whose only visible identifier is a placeholder or an unassociated nearby label — use a proper `<label for>` or `aria-label` instead. (PR #100)
- **Inconsistent lockfile-strict installs**: flag a dependency-install command that omits the lockfile-strict flag (e.g. `--frozen`) when another install path for the same lockfile in the repo already uses it — every install of the same lockfile should fail fast on drift the same way, not just some of them. (PR #104)
- **Unchecked numeric coercion of external input**: flag `Number(...)` applied to a DOM attribute or user-entered value that is then stored or JSON-serialised without a `Number.isFinite` guard — `JSON.stringify(NaN)` is `null`, silently indistinguishable from a genuinely absent value. (PR #108)
- **Inconsistent fail-fast on element lookups**: flag a `querySelector`/`getElementById` result dereferenced with no presence check when the same file already throws a clear diagnostic for a similar lookup — guard every such lookup the same way. (PR #108)
- **Prose contradicting a restated concrete value**: flag a dimension, ordering, or enumeration stated one way in prose when the code (or elsewhere in the same document) states it the other way. (PR #108)
- **Prototype-chain reachable keys from parsed input**: flag a loop over `Object.keys()` of an externally-parsed object that gates each write with a truthiness check (`if (target[k])`) — a key like `__proto__` passes through the prototype chain and the write pollutes the prototype. Gate on `Object.prototype.hasOwnProperty.call(target, k)` (or an explicit allowed-key set) instead. (PR #113)
- **Ambiguous log line across multiplexed code paths**: flag a warning/error/recovery log emitted from a helper or dispatch point that now serves more than one operation or entry point (e.g. one method handling several provider hooks) when the message names neither the operation nor a discriminator — a reader cannot tell which path produced it, especially when one path keeps failing while another succeeds. Include the operation/method name in the message. (PR #118)
- **Linear-scan lookup in a sort-key or repeated-lookup path**: flag a `.index()` call on a list or tuple used as a sort key or evaluated once per comparison/iteration — precompute a dict mapping (or equivalent O(1) structure) once instead of scanning on every call. (PR #138)
- **Stale spec/issue text after implementation deviates from plan**: flag a spec or issue file that still states a file name, scope claim ("no other code references X"), or other concrete fact contradicted by the final code — update the doc to match what was actually built rather than leaving it silently wrong. (PR #138)
- **Incomplete transaction/request outcome handling**: flag a promise wrapper around a transaction or request API that settles on only some of its outcome events (e.g. IndexedDB `oncomplete`/`onerror` but not `onabort`) — an unhandled outcome can leave the promise (and anything gating on it) hanging forever. Handle every outcome event through the same settle path, guarded so it can only fire once. (PR #141)
- **Unverified picker/dialog result cached under an expected key**: flag code that caches whatever a native picker or dialog returns (a file handle, a chosen path) under the key it *expected*, without confirming the result actually matches that key — the user can navigate to or type a different target, and every later operation then silently uses the wrong resource. (PR #141)
- **Stream left open on a mid-write failure**: flag a writable/output stream whose `write()`/`close()` failure path doesn't abort the stream before propagating the error — an open stream can hold a lock or leave a pending write that makes the next attempt unreliable. Abort (best-effort) before rethrowing. (PR #141)
- **Interface comment stronger than the implementation**: flag a Protocol/base-class/contract comment that states a "must" (a required type, invariant, or precondition) the code does not actually enforce — it tolerates the violation and degrades instead. Reword the comment to match what the code does, or make the code enforce the "must". (PR #151)
- **Redundant private-state assertion in a test**: flag a test that asserts an object's private/tracking fields when a public-observable assertion already in the same test (log output, return value, call args) proves the same behaviour — drop the internal assertion. Keep it only where the criterion under test genuinely has no behavioural proxy (e.g. "state X is left unchanged" on a code path that emits nothing either way). (PR #151)
- **Loader registration keyed on a bare filename stem**: flag a dynamic-module/registry loader that derives its registration key from a filename stem alone when the same loader can serve more than one logical root or kind sharing one directory — two different files can share a stem and silently clobber each other's registration. (PR #161)
- **Untested optional-method-absent branch**: flag a dispatch wrapper's "attribute/method absent → no-op or None" branch with no direct test — an existing caller's own pre-guard can mask a broken fallback forever. (PR #161)
- **Untested discriminator/label propagation in a shared wrapper**: flag a generalised or parameterised wrapper's per-caller label/discriminator argument with no test asserting the label actually reaches the output — a wrong or reverted default can pass every other assertion silently. (PR #161)
- **Escaping a delimiter without escaping the escape character first**: flag a custom string-escaping scheme that escapes a separator character without first escaping its own escape character — an already-escaped literal and a freshly-escaped one can still collide. (PR #161)
- **Regression fixture that bypasses the mechanism under test**: flag a test fixture that returns a value captured directly in source (a closure or literal) when the fix under test changes how that value is looked up (e.g. via a registry, cache, or module lookup) — such a fixture can pass identically against the unfixed code. (PR #161)
- **Untested secondary call site for recomputed logic**: flag a feature that recomputes a value on more than one independent trigger (e.g. a replug event and a periodic/new-data refresh) when tests only exercise the first/most obvious trigger — a regression that wires only one path passes silently. (PR #162)
- **Unit-conversion test values too far apart to prove the conversion**: flag a test for a unit conversion (VAT-inclusive/exclusive, currency, scale factor) whose input values differ so widely that skipping the conversion entirely wouldn't change the pass/fail outcome — pick a boundary value where the converted and unconverted results diverge. (PR #162)
- **Unvalidated count/limit parameter breaks a loop's own termination condition**: flag a count/limit argument used only as a "stop once N found" loop condition with no validation that it's positive — zero or negative can never satisfy the condition, so the loop silently scans far more than intended instead of failing fast. (PR #163)
- **Cached token/credential checked against its nominal expiry, no safety margin**: flag a cached token whose validity check uses the server-reported expiry exactly — clock skew or request latency can race it; apply a margin (e.g. 90% of nominal lifetime) as already established elsewhere in this codebase. (PR #163)
- **Structurally-identical sibling loop left untested**: flag two separate but identically-shaped loops or functions (e.g. two independent pagination loops) where only one has dedicated test coverage — a regression in the untested one passes silently since the shapes look interchangeable but are separate execution paths. (PR #163)
- **HTTP 200 body trusted without checking the API's own success/error envelope**: flag code that indexes into a parsed JSON response without first checking an endpoint's own success/error field — an application-level failure arriving as HTTP 200 causes an unhandled KeyError/TypeError instead of routing through the exception handling built for transport/status failures. (PR #163)
- **Third-party exception type reused for an application-level failure**: flag code raising a dependency's own exception class (e.g. `httpx.HTTPError`) to signal a business-logic failure when the repo already has its own exception type for this — conflates a real transport fault with an application error under any generic handler for the third-party type. (PR #163)
- **Silently skips a spec-documented log line on a fallback path**: flag a no-match/fallback code path that returns early without a warning log its own spec explicitly requires — makes a degraded/fallback cycle indistinguishable from a healthy one in production logs. (PR #163)
- **Test proves a call happened but not what it carried or how many times**: flag a test for a retry-then-give-up or refresh-and-retry behaviour that only asserts the final outcome or a mock's call count, without checking the actual argument/header/payload used on each call or the exact number of attempts — a regression using a stale value, or looping/never-retrying, can still pass. (PR #163)
- **Import-time logging configuration reset via a newly-reachable import path**: flag a module that calls `logging.config.dictConfig()` at import time when a new code path (e.g. a dynamically-loaded extension) can cause it to be imported for the first time after file logging has already been configured — silently resets the file handler app-wide. Only modules imported eagerly at startup should call `dictConfig()`; anything reachable only through a dynamic loader must not. (PR #164)
- **Unhashable/non-string value crashes a dict-membership config check**: flag a config validator that checks `value not in {...}` (or similar dict/set membership) without first confirming the value's type — an unhashable type (e.g. a YAML list) raises `TypeError` instead of the intended validation error. Guard the type before the membership check. (PR #164)
- **New config validation branch with no test coverage**: flag a newly-added config-validation branch (a required field, type check, or boundary condition) with no test exercising invalid/missing/blank values for it — every other fixture in the test file supplying only valid values lets a broken validator pass silently. (PR #164)
- **Production extension file never exercised through the real loader**: flag a new operator-facing dynamically-loaded extension whose tests only import it directly or load a synthetic fixture through the loader — nothing proves the shipped file at its real path is discoverable by the shared loader's marker-method detection and lifecycle wiring. Add an integration test that loads the actual shipped file. (PR #164)
- **Incomplete sys.modules eviction misses a transitively-imported module with its own import-time side effect**: flag a test that evicts specific modules from `sys.modules` to force a fresh import (proving an import-time side-effect fix) without accounting for every other module the same code path imports that could carry an equivalent side effect — the test then passes or fails depending on collection/run order instead of proving the fix. Pre-warm the safe ones before evicting the ones under test. (PR #164)
- **Silent schema-rename data loss via permissive extra-key handling**: flag a config/settings model without strict unknown-key rejection when a field is renamed or moved — a leftover key from before the rename is silently dropped instead of failing loudly, which can silently degrade behaviour (e.g. losing a configured provider) with no visible error. Apply strict rejection consistently across config models, matching any sibling model that already does. (PR #164)
- **Unvalidated external API value cached without a sanity check**: flag a numeric value read directly from a third-party API response and cached/used downstream without checking it's finite and within a sane range (e.g. positive) — a malformed payload (negative, zero, NaN, or infinite) can silently corrupt a comparison or downstream calculation. Validate before caching, treating invalid data the same as "no data available." (PR #164)
- **Validated inputs still produce an invalid derived value via arithmetic overflow/underflow**: flag a computed value built from already-validated finite/positive inputs (multiplication, division) that is itself never re-checked for finite/positive before being cached or used — an extreme-but-valid input can still overflow the arithmetic to infinity or underflow it to zero. Validate the derived value too, not just its inputs. (PR #164)
- **Progress watermark committed despite an aborted operation**: flag a cursor/watermark/last-seen value advanced before confirming the guarded operation actually completed — an early return after committing it makes an unchanged input on the next call look identical to one already processed, silently suppressing the retry that return was supposed to allow. (PR #168)
- **Untested tie-break boundary in an inclusive comparison**: flag a `<=`/`>=` (or other inclusive) comparison deciding between two branches with no test at the exact equal-value boundary — a regression to the strict operator changes which branch fires only at that boundary and would pass every other test unnoticed. (PR #168)
- **Timestamp sampled after a moved/restructured await instead of before it**: flag a refactor that relocates a `now()`/timestamp capture into a closure or helper invoked after an `await` that used to happen after the timestamp was taken — even with no logic change, a slow awaited call can now shift which records pass a since-timestamp filter or how fresh a freshness marker looks. Capture the timestamp before the await, not inside code that runs after it. (PR #175)
- **New wrapper around an already-tested generic mechanism has no test of its own for that mechanism**: flag a new validating/adapting wrapper placed in front of an existing generically-tested cross-cutting mechanism (e.g. failure deduplication, retry, caching) with no test proving the new wrapper specifically produces output that mechanism handles consistently across repeated calls — testing only the generic mechanism in isolation doesn't prove a newly added seam composes with it correctly. (PR #175)
- **Comment or test name still describes a return contract a type change already replaced**: flag a comment or test name stating a function "returns None" (or similar) for a case that, elsewhere in the same diff, now returns a different typed value instead — update every description of the old contract, not just the code that changed it. (PR #177)
- **Single test exercises only one of several distinct paths into the same catch-all exception or failure branch**: flag a test proving an `except` block or typed-failure branch fires via only one triggering mechanism (e.g. a transport-level exception) when the same catch also handles a documented second cause (e.g. an HTTP status error via `raise_for_status()`, or a spec/docstring listing multiple causes like "404 or HTTP error") that no test exercises separately — add one test per distinct triggering path, not one test claiming to cover the branch as a whole. (PR #177)
- **Comment enumerating a group of fields becomes stale when one member's handling changes**: flag a comment listing several fields/parameters as sharing a validation or protection rule (e.g. "X, Y, Z all need isfinite") when a diff removes one member (X) from ever going through that shared path — the comment still claims it's protected there. Update the enumeration to match, not just the code. (PR #179)
