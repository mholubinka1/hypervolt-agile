# Migrate from Poetry to uv

## Problem Statement

The project's Python tooling (dependency resolution, lockfile, pre-commit hooks, CI, Docker
build) is built entirely on Poetry. The operator wants to move to uv instead, and to update
dependencies to their latest versions as part of the same piece of work.

## Solution

Two sequential slices. First, swap every Poetry-driven surface for its uv equivalent with
dependency versions held identical to what's pinned today — proving the tooling change alone
works before anything else changes. Second, once that's green, run uv's own upgrade mechanism to
bring dependencies (and pinned pre-commit hook revisions) up to their latest compatible versions,
as a distinct, separately-bisectable commit.

## User Stories

1. As the operator, I want the project's dependency tooling to be uv instead of Poetry, so that
   installs are faster and the toolchain matches where the wider Python ecosystem (and GitHub's
   own Dependabot/Dependency Graph support) has moved.
2. As the operator, I want the tooling migration and the dependency version bump kept as separate
   steps, so that if CI breaks afterward I know immediately which change caused it.
3. As a developer, I want `pyproject.toml`'s declared Python floor to match what Docker and CI
   actually run, so the declared support matrix isn't lying about what's tested.
4. As the operator, I want Dependabot and GitHub's Dependency Graph to keep working against the
   new lockfile without a gap in coverage.

## Implementation Decisions

**`pyproject.toml`** — hand-converted from `[tool.poetry]` to PEP 621, not run through an
automated converter (predictable, and every claim gets verified by actually running `uv lock`/
`uv sync` rather than trusted from documentation alone):

- `[project]` replaces `[tool.poetry]`: `name`, `version`, `description`, `readme` carry over
  unchanged; `authors` becomes the PEP 621 list-of-tables form
  (`[{ name = "...", email = "..." }]`); `requires-python` replaces the `python = "^3.11"`
  constraint — raised to `>=3.13,<4.0` (was declaring 3.11+ while Docker/CI only ever ran 3.13;
  this closes that gap, applied consistently everywhere else the floor is declared, listed
  below). Runtime dependencies move to a `dependencies = [...]` array, each Poetry caret
  constraint translated to its explicit PEP 440 equivalent (e.g. `^0.28` → `>=0.28,<0.29`;
  `^3.12.15` → `>=3.12.15,<4.0.0`) — already-explicit ranges (`tzdata`, `websockets`, `mypy`,
  `isort`) carry over verbatim.
- `[tool.poetry.group.dev.dependencies]` becomes a PEP 735 `[dependency-groups]` table with a
  `dev` key; `bandit`'s `extras = ["toml"]` becomes the inline `bandit[toml]` extra syntax.
- `[tool.uv]` gains `package = false` — this project has never been an installable/publishable
  package (Poetry's `package-mode = false` did the same job), so `[build-system]` is dropped
  entirely rather than translated; uv only needs a build backend when it's actually building the
  project into a wheel for install, which non-package mode never does. Verified empirically
  during implementation, not assumed.
- Every other existing `[tool.*]` table (`ruff`, `mypy`, `bandit`, `pytest`, `coverage`) is
  untouched except `[tool.mypy]`'s `python_version = "3.11"` → `"3.13"`, matching the
  `requires-python` change above.

**`uv.lock`** — generated by `uv lock` against the converted `pyproject.toml`; this is the slice-1
commit's proof that dependency resolution succeeds with today's exact versions expressed in uv's
own constraint syntax.

**`.pre-commit-config.yaml`** — `poetry-check`/`poetry-lock` (python-poetry/poetry repo) and
`poetry-export` (python-poetry/poetry-plugin-export repo) are replaced by `astral-sh/uv-pre-commit`'s
`uv-lock` and `uv-export` hooks respectively (`uv-export` keeps the same
`args: ["-f", "requirements.txt", "-o", "requirements.txt"]` shape). No other hook changes.

**`Dockerfile`** — the builder stage's `pip install poetry` + `poetry install --no-root --only
main` sequence becomes an official `uv` install (e.g. the static binary via the documented
`COPY --from=ghcr.io/astral-sh/uv` pattern, or `pip install uv` — decided during implementation
by checking what keeps the image smallest, since the whole point of the multi-stage build is a
slim runtime image) followed by `uv sync --frozen --no-dev` (or uv's equivalent
production-only/no-root flags) targeting `.venv` the same way `POETRY_VIRTUALENVS_IN_PROJECT=true`
did, so the final stage's `COPY --from=builder /app/.venv ./.venv` and the `CMD
[".venv/bin/python", ...]` entrypoint need no change at all — uv's project-venv model already
lands the interpreter at the same `.venv/bin/python` path.

**`.github/workflows/ci-checks.yml`** — `actions/setup-python@v7` (pinned to `'3.11'`) becomes
`'3.13'` to match the new floor; `pip install poetry` + `poetry install` becomes
`astral-sh/setup-uv` + `uv sync`; every `poetry run <cmd>` becomes `uv run <cmd>`; `poetry check`
/ `poetry check --lock` become `uv lock --check` (uv's own lockfile-consistency check covers both
concerns Poetry split across two commands). `ci-arm64.yml` needs no change — it only invokes
`docker buildx build`, and Poetry/uv both live entirely inside the Dockerfile it builds from.

**`.github/dependabot.yml`** — `package-ecosystem: pip` becomes `package-ecosystem: uv` (GitHub
added native uv ecosystem support; confirmed via GitHub's own 2026-04-23 changelog entry, "Dependabot-based
dependency graphs for Python"). The existing `python-packages` group/schedule shape is unchanged.

**`README.md`** — "Python 3.13+ with [Poetry]... (for local development)" section updates its
install/run commands (`poetry install --with dev` → `uv sync`; `poetry run python app/main.py
...` → `uv run python app/main.py ...`) and the Poetry link/mention.

**Slice 2 — dependency update**: once slice 1 is green, `uv lock --upgrade` brings every
dependency (runtime and dev group) to the latest version satisfying its `pyproject.toml`
constraint; `uv sync` reflects that into the local environment; pre-commit hook revisions in
`.pre-commit-config.yaml` (mypy, isort, black, ruff, pre-commit-hooks, markdown-link-check,
gitleaks, bandit, and the new `uv-pre-commit` entry itself) are bumped to their current latest
tags the same way the existing `update-dependencies` skill already does for hook revisions
(checked by hand this slice, not by invoking that skill — it doesn't detect uv projects yet, see
Out of Scope). Anything a constraint's upper bound blocks from reaching the newest release (a
genuine major-version bump) is reported, not silently forced past the declared constraint.

## Testing Decisions

No new automated tests — this is tooling/infra, not application behaviour, and nothing here has
a pytest seam. Verification is direct command execution, empirically checked at each step rather
than assumed from documentation:

- `uv lock` succeeds (proves the converted `pyproject.toml` resolves).
- `uv sync` succeeds and `uv run pytest tests/` passes all 197 existing tests unchanged.
- `uv run pre-commit run --all-files` passes (proves every hook, including the new `uv-lock`/
  `uv-export` pair, is wired correctly).
- A local `docker build .` succeeds and the resulting image's `.venv/bin/python` still runs
  `app/main.py --help`-equivalent smoke (or as close to a real smoke check as is practical without
  live charger credentials in CI).
- CI itself (`ci-checks.yml`) going green on the pushed branch is the actual acceptance check for
  the GitHub Actions changes — cannot be fully verified locally.

## Out of Scope

- Fixing the `update-dependencies` skill's Poetry-only ecosystem detection to recognise uv
  projects — that skill lives in a separate repo (`C:\Users\mehol\git\skills`), not this one;
  flagged for a separate follow-up request, not part of this PR.
- Any application-level dependency migration prompted by a major version bump surfacing during
  slice 2 (e.g. if `pydantic` or `httpx` had a breaking major release available) — report it,
  don't silently absorb a breaking change into a "just update dependencies" slice.
- Publishing this project as an installable package (`[tool.uv] package = false` keeps the
  current non-package, app-only shape).
- Raising the Python floor any further than 3.13, or changing the Docker base image version.

## Further Notes

- ADR recorded for this: Poetry → uv is a genuine cross-cutting infra decision (touches CI,
  Docker, Dependabot, and daily dev workflow) with a real trade-off (uv's speed and growing
  ecosystem support vs. Poetry's maturity and the working status quo) — meets the "hard to
  reverse / surprising without context / genuine trade-off" bar.
- `uv` is already installed locally (`uv 0.11.28`), so every claim in this spec about command
  behaviour gets verified by running the real command during implementation, not left as an
  assumption carried over from research.
